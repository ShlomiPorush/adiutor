# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **The tray app for Windows**: an icon in the notification area that runs the sync. A click shows the last sync of T3 and of security with its time, the last good sync and the next one, with Sync now, Pause (1 hour, 4 hours or until you resume) and Resume, Open Adiutor, Settings and Quit. It checks in with Adiutor every minute, so Sync now in Adiutor reaches it within a minute, and syncs every 3 hours by default. Settings connect Adiutor and T3 and hold the overview folder, the schedule, start with Windows (on by default) and the language, Hebrew or English; they show each value as the sync uses it, and one set by the environment is locked there. The theme follows Windows. It shows a Windows notification only when two scheduled syncs in a row did not complete, or a connection ended. It installs per user through Velopack, updates itself from this repository's GitHub Releases when no sync is running, and keeps the sync's data folder when it is uninstalled. Quit lets a running sync finish first.
- **The sync reads T3 itself**: `node dist/sync/adiutor-sync.js t3-connect` gives the sync a read-only T3 session of its own for 30 days, kept with its Adiutor connection and readable by you only; it shows in T3 under Authorized clients. The sync reads T3's project list with it, renews it on its own before it ends, and keeps the last good list for when T3 does not answer (the run then says how old the list is). When T3 refuses the session, or its address or CLI answer as another T3, the sync stops reading T3 until you run `t3-connect` again. `t3-disconnect` ends the session.
- **`status` and `disconnect`**: `status` shows both connections, the last run per part, the last good sync (both parts accepted in the same run), and each setting with where it comes from. `disconnect` ends the sync's connection in Adiutor, then forgets it; when Adiutor's answer is lost, it tries again on the next command.
- **One run at a time**: a second `run` answers that a run is going, with its start time, and runs nothing.
- **`--json`** on `run`, `status`, `connect`, `disconnect`, `t3-connect` and `t3-disconnect`: one JSON object per line, ending in one result, for the tray app (`docs/sync.md`, "Machine-readable output"). Each run's result is kept in `status.json` in the sync's data folder.
- **Sync now**: ask for a sync from Adiutor, in Settings, Sync or on the sync card. The sync on your computer takes it at its next check-in, within a minute, through the tray app: the engine's new `checkin --json` sends the tray's state and keeps the request it gets, and `run --request <id>` runs it. Settings, Sync shows the request (waiting for the computer, running, done with each part's result, partly done, failed, cancelled, or the computer stopped answering), Cancel while it waits, the computer's last check-in, its pause and its next scheduled sync, and says when the computer has not checked in for three minutes. Until a computer checks in, Sync now stays disabled with the reason and the page says where the tray app comes from. Each request and each cancel is in the activity log, and so is every check-in, as every agent call is.
- **The tray app's installer on every release**: each release carries `AdiutorSync-win-Setup.exe` and the update feed of the tray app on its GitHub page, built from the release's own commit with Node.js 24.22.3 inside (the version the sync targets, its checksum checked when the release is built, its license included). An installed tray updates itself from the newest release, downloading only a small delta package when one fits. Before the first such release, turn on immutable releases in the repository's settings (Settings, Releases, Enable release immutability), so a published installer can never be replaced: until then a release stops before it publishes anything.
- **Snoozed threads**: a thread snoozed in T3 shows as snoozed on its item, with the time when T3 gives one. It changes no status the sync decides.
- **A settings file**: the sync also reads `settings.json` in its data folder (`%LOCALAPPDATA%\adiutor`), below the env file and the environment. T3's address is a setting (`ADIUTOR_T3_URL`, default `http://127.0.0.1:3773`), and the T3 CLI defaults to where T3 installs it.

### Removed

- **`run --projects` and `prompts/reconcile.md`**: the sync no longer needs an agent to list T3's projects. Run `t3-connect` once on the PC that runs the sync, then `run` without `--projects`.

## [0.2.1] - 2026-11-16

### Changed

- **`ADIUTOR_OAUTH_SECRETS` is no longer needed**: the cookie keys of the authorization server for agents are derived from `ADIUTOR_AUTH_SECRETS`, one per version, so rotating the auth secrets rotates them too. Deploy this release without adding anything to `.env`. If you added `ADIUTOR_OAUTH_SECRETS` for 0.2.0, delete the line: until you do, the server only logs a warning at start. An agent approval under way during the upgrade from 0.2.0 may have to start again; agent connections stay.

## [0.2.0] - 2026-11-16

### Added

- **Passkeys**: sign in with a passkey alone, with your fingerprint, face or device PIN, instead of the password and the code. Add, rename and remove passkeys on the Account page (up to 20); the browser must support passkeys to add one or sign in with it, and listing, renaming and removing work in any browser. The password and the authenticator app keep working. A passkey belongs to the host name of `ADIUTOR_PUBLIC_URL`: changing that host name makes every passkey stop working. Adding a passkey needs two-factor on. Each change, and each sign-in with a passkey, is in the activity log. The server's password reset keeps passkeys, so after a restore or a lost device check them on the Account page.
- **Agents and the sync connect by approval**: each agent, MCP client and the sync asks once, and you approve it in the browser on Adiutor's code page or approval page, choosing its areas (read and write; the sync area for the sync). Settings, Agent access shows how to connect with your address: the MCP address and the Claude Code command, the sentence that installs the agent skill from `<address>/agents/skill/`, and the sync bundle's `connect` and `setup-mcp` commands. It lists every connection with its areas and last use, disconnects one or all, turns agents on or off, and sets the idle days (90 by default) after which an unused connection ends. A connection also ends when the password is changed or reset, two-factor is turned off, or `ADIUTOR_PUBLIC_URL` changes. Agents reach only what their areas open; the activity log, settings, deleting and changing a stage stay the owner's. Every agent call is in the activity log. No token is ever shown or printed.
- **The sync says when it is disconnected**: when no connection holds the sync area, the morning message, the sync card and the overview say that the sync must be connected again on the computer that runs it, with the time of its last good run; the sync card then opens Settings, Agent access.
- **`ADIUTOR_OAUTH_SECRETS`, required**: the cookie keys of the authorization server for agents. The server refuses to start without it: add it to `.env` before you deploy, with the command in `docs/deployment.md` (step 2), which never overwrites a value that is there. The server now also refuses a current key (the first one listed in `ADIUTOR_AUTH_SECRETS`, `ADIUTOR_SETTINGS_KEYS` or `ADIUTOR_OAUTH_SECRETS`) that looks like an example placeholder, and says how to replace it while keeping it as an older version.

### Changed

- **Every agent and the sync connect once again: agent keys end.** From this release on, Adiutor refuses every agent key on `/api/v1` and `/mcp` before any of its code runs, and no new key can be made: the old agent skill, `adiutor-sync connect --for`, the sync and Claude Code or Codex set up with a key stop until you connect them again. Do it in this order (`docs/deployment.md`, section 10):
  1. Add `ADIUTOR_OAUTH_SECRETS` to `.env`, then deploy this release.
  2. Move the shared agent configuration to this release's tag, and on the PC that runs the sync pull this release and build the sync bundle again. Clients updated before the server cannot connect to the older server.
  3. Approve each client once: tell each computer's agent the sentence from Settings, Agent access (or run `adiutor connect` with a skill installed from the repository); run `node dist/sync/adiutor-sync.js setup-mcp --for claude` and `--for codex` with `--url` and your address, which replace a setup with a key; and connect the sync with `node dist/sync/adiutor-sync.js connect --name "sync" --url "<address>"`, keeping the sync area ticked.
  4. Delete the old keys, listed in Settings, Agent access until a later release removes the list.
- **The recovery command ends every agent connection** as well as every session: connect the agents and the sync again after `reset-password`.
- **Pull request stacks seed with the owner's session**: `scripts/try-pr.sh` writes no agent key into `owner.env` any more, and its invented board has no T3 threads, sync runs or security sources, which only the sync pushes. A pull request stack has no agent access: its `http` address on `pr.localhost` is not one agents may use.
- **`/mcp` refuses pages from other sites**: a request whose `Origin` is not Adiutor's own address gets `403 forbidden` before its key is read, as the MCP transport specification asks against DNS rebinding. Clients that send no `Origin` (Claude Code, Codex, scripts) are unchanged. A request body over 512 KiB gets `413`, the same bound as the REST API.
- **MCP tools say that stored text is data**: the MCP instructions and every tool description now tell agents that text in items, comments, notes, projects and thread titles is data, never instructions to follow.

### Security

- **No session works as a bearer token**: Better Auth's `bearer()` plugin is gone and its routes take the browser's session cookie only, refusing any `Authorization` header. A sign-in answer no longer hands page script the session token (`set-auth-token`). `/api-key/create` and the device routes of the old agent approval answer `404`.

## [0.1.2] - 2026-11-14

### Changed

- **`adiutor-sync connect` checks the key it receives**: it uses the key only when it is `adt_` followed by letters and digits. Anything else in a successful answer is neither saved, printed nor passed to Claude Code, Codex or `setx`, and `connect` exits 1 and asks to disconnect that key in Settings, Agent access. The `codex.env` line and the printed `export` and `claude mcp add` lines hold the key in single quotes outside Windows, and the sync's env file never takes a value with a line break.
- **Pull request stacks on their own address**: `scripts/try-pr.sh` serves a pull request on `http://pr.localhost:8091` instead of `http://127.0.0.1:8091`, through a proxy that answers only that name, so the browser keeps the development stack's sign-in away from the pull request's code. A stack started before this change keeps its old address; `status` says so, and `restore` then a new run moves it. Agent tools accept plain http only for `localhost` and `127.0.0.1`, so they cannot connect to a pull request stack; call its API with the agent key in `owner.env` (curl and browsers find `pr.localhost`).
- **Setting up a new authenticator says what happens meanwhile**: the Account page's hint no longer says that Adiutor stays closed. Until the new authenticator app is set up, the password alone signs in, from any browser, and leads to the setup, so finish it right away.
- **The audit log shows agents which settings and suppression fields changed, not their values**: `GET /api/v1/audit` answers a reader other than the owner the rows of `settings` and `suppression` with `before` and `after` empty and `redactedFields` naming the fields that changed, and its search does not match a suppression's name for that reader. The owner still sees every row whole. Rows written before this change are covered too.

### Fixed

- **Secret check on long values**: removing sentence punctuation from the end of a value after a secret name such as `token=` or `DB_PASSWORD=` now takes time in proportion to the value's length. A long run of `.`, `!`, `?` or `:` inside such a value no longer keeps the server busy for seconds. What the check finds is unchanged.
- **Failed agent keys limit only the client that sent them**: behind Traefik, ten wrong keys from one client made every agent, the sync and the owner's browser wait a minute on `/api/v1` and `/mcp`. The limit now counts the client address from `X-Forwarded-For` when the connection comes from a proxy in `ADIUTOR_TRUSTED_PROXIES`, and applies only to requests with an `Authorization` header, so the owner's browser session is never limited by failed keys.
- **The sync keeps a deleted item's threads untracked**: a snapshot that names such a thread as the parent of a linked thread no longer moves that link onto it. The link stays on the child thread, and the run counts it as `childLinksSuppressed`.
- **Secret check on long runs without spaces**: the checks for credentials in URLs and for JWTs now take time in proportion to the text's length. Two edge cases may no longer be found: a JWT directly after `-` (`id-eyJ...`), and credentials after a URL scheme longer than 32 characters.
- **Every new agent key has an end**: `POST /api/auth/api-key/create` now refuses a request without a number `expiresIn` (`400 EXPIRES_IN_REQUIRED`), so each key ends 1 to 365 days after it is created. `adiutor-sync connect` and the agent skill already send it; existing connections and keys are unchanged.
- **Ids in capitals**: a UUID sent in capitals now works like the same id in lower case. Changes made through it appear in the item's history and in the overview's agent updates, the activity log stores it in lower case, the same project id no longer clears an item's goal, linking a thread again no longer answers `conflict`, and a project read through it shows its goal. Rows stored earlier with an id in capitals appear in the item's history and the overview too.
- **Sync snapshots cannot carry times in the future**: the server refuses a pushed time more than 5 minutes ahead of its clock. Before, one record dated in the future stood against every later snapshot, so security counts, the open Issues count or a thread's status stopped updating, and a thread's last activity could keep overriding a status the owner set. A `collectedAt` in the future refuses the whole snapshot (`400 validation_failed`, the run recorded as failed); a single thread or repository with such a time is refused alone and reported in `errors` as `time_in_future`. Records stored before this change are kept as they are. Keep the PC's clock set automatically.

### Security

- **Two-factor is set up with an authenticator app only**: `POST /api/auth/two-factor/enable` with a `method` other than `totp` answers `400 TOTP_ONLY`. Sign-in codes sent to Telegram still work at sign-in when the owner turns them on.

## [0.1.1] - 2026-11-13

### Fixed

- **Runs on PostgreSQL 16**: 0.1.0 stopped at its first query on PostgreSQL 16 (`unrecognized configuration parameter "transaction_timeout"`). Each connection now limits every statement to 15 seconds and an idle transaction to 15 seconds, both known to PostgreSQL 16; Adiutor needs PostgreSQL 16 or newer. The verification and pull-request stacks run PostgreSQL 16.

### Changed

- **New since your last visit is the owner's, across browsers and devices**: a visit on the phone counts on the desktop the next time the overview opens, and an open overview keeps its list. Adiutor no longer sets its `adiutor_browser` cookie, and `GET /api/v1/session` no longer answers `browserId`. Existing visits keep their times.

## [0.1.0] - 2026-11-13

### Added

- **Server**: a TypeScript server on Node.js 26 that refuses to start without a database URL, a public URL and its versioned keys (`ADIUTOR_AUTH_SECRETS` for sign-in, `ADIUTOR_SETTINGS_KEYS` for secrets stored in Settings), or with a `BETTER_AUTH_*` variable set. It applies its database migrations on start, logs a failed migration with PostgreSQL's message, and answers `/healthz` when the database answers. Needs PostgreSQL 17 or newer: every transaction ends after 30 seconds (`transaction_timeout`). Unexpected errors are logged as their class, SQLSTATE and error code only, never with query text or parameters.
- **Container image and Compose files**: one image, run as `node` on a read-only root file system with no capabilities; a production Compose file behind Traefik with the database outside it (`ADIUTOR_TRUSTED_PROXIES` names the proxy); a development stack with its own PostgreSQL, which generates its database password and keys on the machine (the repository holds examples only), publishes its port on every interface for a reverse proxy, and reads an optional, ignored `.env.dev` for overrides.
- **Projects, goals and items** with Hebrew and English labels for every stage, item status, type and severity. Every write goes through a service and writes an audit row in the same transaction. Agents, the bot and the sync never delete and never change a stage; they propose one. Items use optimistic concurrency by version. Deleting an item or project suppresses its T3 threads or project, so the sync never recreates it.
- **Secret check** for text from agents and the bot: known token formats, private keys (redacted whole), credentials in URLs, environment-style secret assignments, IPv4 addresses outside documentation ranges and the private domains from Settings are refused with `secret_suspected`; thread titles from the sync are redacted instead.
- **Start of thread** in one transaction: finds, links or creates the thread's item and sets it in progress; a retry or a race returns the same item; child threads are refused.
- **Sync** from the owner's PC: the sync tool (`dist/sync/adiutor-sync.js`, Node.js 24) runs the `overview` collector, reads every T3 project's threads through the T3 CLI, and sends them with each repository's security alert and open Issues counts. The server applies a snapshot per record, the owner always wins (a delete during a sync run is never undone), older records and counts never replace newer ones, and a failed read never overwrites known counts. Projects that could not be read fully are reported as such: the run is partial, their items are not decided, and the board's freshness comes from the last complete run. The agent key is never accepted on the command line, printed or passed to a child process. `prompts/reconcile.md` is the prompt of the T3 scheduled task that runs it every morning.
- **HTTP API** under `/api/v1` and an **MCP server** at `/mcp` (Streamable HTTP, stateless) with fifteen tools. Agents and the sync use agent keys (`adt_` and 64 letters, stored hashed), each approved by the owner in the browser; the browser uses the owner's session. Browser changes need a CSRF header, failed keys are rate limited, a request body is read by the application only after its key or session is accepted, and errors carry stable codes. See `docs/api.md`.
- **Sign-in** with Better Auth: one owner account with a username, a password and a mandatory authenticator app (TOTP); the authenticator app shows the username. The first run creates the account, sets up the authenticator with a QR code or the key as text, and shows 10 backup codes once (copy, download, "I saved them"). Sign-in takes an authenticator code or a backup code, or, when the owner turns it on in Settings, a code sent to the owner's Telegram chat. A browser is signed out after 30 days without Adiutor open (1 to 90 in Settings); background updates never extend a session. An Account page, opened from the account menu, lists the signed-in browsers, changes the password, makes new backup codes, sets up a new authenticator, and signs out the others or all; this browser signs out from the account menu, which asks about unsaved changes first and keeps them when the sign-out fails. Sign-in is rate limited and checked against cross-site requests, and every sign-in, sign-out, enrolment and password change is in the activity log. Locked out: `node dist/server/cli.js reset-password` on the server prints a new password once and signs out every browser; two-factor stays.
- **Agent approval in the browser**: `node dist/sync/adiutor-sync.js connect --name <name> --for <sync|claude|codex>` asks Adiutor for a code and opens `/connect/device`, where the owner, signed in with two-factor, compares the code and allows or denies. The command then gets one key with that name, ending after `--days` (1 to 365, default 90), and ends its temporary session at once. `--for sync` writes the key to the sync's env file, readable by the owner only; `--for claude` adds Adiutor to Claude Code itself with `claude mcp add` at user scope, replacing an older `adiutor` entry; `--for codex` sets `ADIUTOR_AGENT_KEY` (with `setx` on Windows, in an owner-only `~/.config/adiutor/codex.env` elsewhere) and adds Adiutor with `codex mcp add`. When `claude` or `codex` is missing or fails, it prints that setup once instead. Settings, Agent access shows the commands, lists each agent with its end date and last request, and disconnects one or all at once; there is no button that creates a key. The Account page names a leftover `adiutor connect` session and signs out any single session. Approvals, denials, keys and ended sessions are in the activity log. Built on Better Auth's device authorization, bearer and api-key plugins.
- **Notes**: knowledge the owner and his agents keep and find again: a title, a Markdown body of up to 100,000 characters, and a project or none. Agents find, read, create and edit notes over the API and four MCP tools (the owner's notes included) and never delete one; every change is kept as a version, and only the owner restores a version or deletes a note, at the version he saw. A project with notes cannot be deleted until they move. Text from agents goes through the secret check, and the activity log records each change without the body. See `docs/api.md`, Notes. In the web UI, Notes in the navigation lists them with a search, a project or general-notes filter, a Written by filter and one Sort button; a note has its own page with the title, the project and a Markdown text that is written and previewed (each block in its own direction, code left to right, no raw HTML, images as links), saved through the save bar, and kept as typed when an agent changed the note meanwhile; its versions open in a window with Restore and Undo, and Delete asks first. A project's page lists its latest notes, the overview's agent updates show agents' notes (general notes in a group of their own), and the activity log links to a note and counts it under its project.
- **Telegram bot**: the owner sends plain text to the bot and it lands in the inbox, with a reply that links to the new item and a **Make it a note** button: a press moves the text into a general note and closes the item as not relevant, with a comment that links the note (only while the item is still as captured; a second press moves nothing). A repeated or redelivered update never files twice. Other chats get no answer; text that looks like a secret is refused without being repeated. On when a bot token (stored encrypted) and a chat id are set in Settings.
- **Morning message** at 08:00 Asia/Jerusalem, Sunday to Friday: what waits on the owner (with links), what is new since the last visit or the last message, up to two security lines, and the last T3 sync when it is stale; one line when nothing needs the owner. Times follow the Date Format and Time Format settings, in Hebrew or English. Sent at most once a day: a send that may have gone out is never resent, a refused one is retried until 11:00, and a later start skips the day. Settings, Telegram shows the bot's status and sends a test morning message at once without touching the 08:00 run.
- **Web UI** in Hebrew (right to left, the default) and English, light and dark, for desktop, the icon-rail width and phones: the overview, the home screen, across the whole width (the inbox count and the last T3 sync above two columns: waiting on you with stage proposals to accept or reject, then the security lines; new since the last visit, then agent updates; projects with goal progress and open Issues across both below; one column with waiting on you first below 1001px, in the same order for the keyboard and screen readers), all projects by stage (with a Sort button at every size that keeps one order with the column headers, and on a phone one stage picker named by its value instead of the chips), a project (stage set by the owner with Undo, proposals, goals, items by status, security sources, delete), an item over any page with its own address (status, type and project with Undo, the project from a picker; a title that grows to show it whole; title, details and comments saved on purpose, never over a change made meanwhile; linked T3 threads; history), the inbox (each row moves its item to a project from a picker, with Undo), the archive and the activity log, and Settings in sections, each with its own address (`/settings/<section>`) under General, Security, Integrations and Sync: General (language, date and time format, closed-item days, how long a browser stays signed in), Agent access, the secret check's private domains, Telegram, the sync status and suppressions; below 1024px a sticky picker replaces the section list. One save bar covers every section: changes stay while moving between sections, a dot marks each section that holds one, and a refused field opens its section. Each setting is a row whose control fills its column; a value that differs from its default is marked Changed with Reset to default, which changes only the unsaved draft (secrets and the owner's own values, such as the chat id and the private domains, have none; the chat id has Clear). A setting that an environment variable sets stays in place, disabled, with a neutral tag beside its name and the variable under it. Telegram opens with its status and the test message; while Telegram is not on, the test and the sign-in codes are locked areas that say what is missing and lead to the bot token. The password is changed in a dialog that checks its fields first and asks before it drops what was typed. List actions sit at the end of the list's head: Sign out other browsers and Sign out everywhere, Disconnect all, and Remove all for suppressions, each asking first. The private domains are value chips. The frame: a top bar with the logo and the page title, the page's main action beside it (on a phone, on the title's line), quick add and the bell; a sidebar that folds into an icon rail (Ctrl+B) and stays folded after a reload; a card with the last T3 sync; an account menu with the theme (light, dark or the system's) and sign-out; on a phone a bottom tab bar with every other page under More. Choices among projects use one picker: full keyboard use with type-ahead, a search above more than ten choices, kept on screen, and closed by Escape or Back before the dialog under it. The bell counts what needs the owner; quick add opens from any page with N, its project from the same picker; pages update themselves. Fonts and icons ship in the image, and the Content-Security-Policy allows only Adiutor's own files.
- **Activity filters**: the activity log narrows by who (you, agents, the Telegram bot, the sync, the system), one agent, an action, a project (its items included) and an item, and by a search over actions, names and who, in Hebrew or English words. Who and the search are always in view, the rest behind a Filters button that counts those in use. Every number, the list's total and each choice's count, comes from the server and is what choosing it lists; Clear filters puts everything back. The filters stay in the address through a reload, Back and Forward, a change of filters starts the list from its top, and `GET /audit` takes the same filters (`docs/api.md`, Audit filters). An agent's name on the overview's agent updates opens its activity, and an item's history has All activity.
- **Workflow scripts and CI**: `scripts/local.sh` for the development stack; `scripts/verify.sh` with repository guards, lint, types, unit and database tests, the image with its health, user and hardening checks, and Playwright end-to-end tests on desktop and phone; `scripts/try-pr.sh` to run a pull request as its own stack with invented data on `127.0.0.1:8091`; a CI workflow and weekly Dependabot updates.
- **Release workflow**: a manual Release workflow on `main` (patch, minor or major, and `dry_run` to check everything and publish nothing). It reuses the newest CI run of the commit on `main` when its latest attempt succeeded, waiting up to 30 minutes for one that still runs; otherwise it runs the whole CI itself (`scripts/ci-result.sh`). A reused run is checked again right before publishing, and the release stops if a newer run appeared. Then `scripts/release.sh`: the `Unreleased` section closed, a release commit and an annotated tag pushed together, `ghcr.io/shlomiporush/adiutor:<version>` then `:latest` with provenance and an SBOM, and the GitHub Release from the changelog section. An existing tag is never moved, and a run that stopped halfway is finished by the next run. `scripts/test-release.sh`, `scripts/test-ci-result.sh` and `scripts/test-release-workflow.sh` run with the guards.
- **Agent skill** (`skill/adiutor`): what agents do in Adiutor and how, for Claude Code and Codex, through the MCP tools when a session has them and otherwise through its own `adiutor` command (Node 20+, Windows PowerShell 5.1 and PowerShell 7, or POSIX sh and curl, with one contract). `adiutor connect` prints a link and a code for the owner to approve in the browser, and `adiutor connect --wait` saves one key per computer user in `~/.adiutor/`, readable by that user only, and ends its approval session at once. The command then calls only the fifteen routes of the MCP tools, names the agent in the activity log with `--as`, never sends a write twice when its answer was lost (`outcome_unknown`), and reports any key or approval session it may have left on Adiutor until the owner has cleaned up.
- **Documentation**: deployment notes (`docs/deployment.md`) and a draft of the agent instructions and MCP connection for Claude Code and Codex (`docs/agent-instruction.md`), awaiting the owner; the instruction text itself is in the agent skill.
