# AGENTS.md

## Project

Adiutor is a personal, single-user project-focus system: an overview board, a Telegram morning message and an MCP server that AI agents use to keep work items current. One application container with PostgreSQL, reachable only over the owner's private network.

**Stage: foundation.** Read these before any change:

- Product requirements: `docs/requirements.md`
- Foundation plan, decisions and status: `docs/project-foundation.md`

The foundation plan is the desired state. Items marked planned do not exist yet. Check the repository before assuming a file, command or feature exists.

UI follows the `v3-ui-style` skill.

## Layout

One pnpm package (no workspace apps).

- `src/server/`: Hono server. `index.ts` starts it, applies the owner's settings (the bot and the morning job when Telegram is on) and builds agent access (`createAgentAccess` on a pool of its own, before Better Auth, which gets its identity hooks; mounted with the skill folder `skill/adiutor` beside `dist/`; on shutdown `server.close`, then the mount's `drain()`, then the pools), `config.ts` reads and checks the environment (the two key families, both required, each refusing an example placeholder, and the agent cookie keys derived from the auth secrets; wiring, the per-field overrides of owner settings; refuses `BETTER_AUTH_*`, `AUTH_SECRET` and the removed `ADIUTOR_AUTH_SECRET`), `cli.ts` is the recovery command (`reset-password`, which builds agent access too, so the reset ends every agent connection), `app.ts` mounts `/healthz`, Better Auth's own handler at `/api/auth`, `/api/setup`, `/api/v1`, `/mcp` and the built UI (`web.ts`: `dist/web` with a page fallback and the Content-Security-Policy) and maps errors; given `agentOAuth` (built by the caller with `agentOAuthMount`, imported as a type only; `index.ts` always passes it, and tests may build an app without it) it also mounts agent access (`oauth/routes.ts`) before `/api/v1`. `healthcheck.ts` is the container health check, `errors.ts` holds the stable error codes, `db/` the Drizzle schema and client (`createDatabase(url, {max})`: a smaller pool of its own, such as the authorization server's storage). The tables of agent connections (`agent_connections`, `oauth_store`, `agent_state` with the issuer fingerprint, the generation and the encrypted signing key, `agent_consent`, `agent_identity_changes`) and the settings `agents_enabled` and `agent_idle_days` are read and written only by `oauth/` (`oauth/sync-status.ts`, which loads nothing of the authorization server, tells the morning read whether a live connection holds the `sync` area); the general settings API leaves the two settings out (`settingsView` in `services/admin.ts`): they are read and saved through `/api/v1/agents/settings`.
  - `auth/`: `auth.ts` (Better Auth 1.7.19 as it documents itself: the username, twoFactor and `@better-auth/passkey` plugins, and `@better-auth/api-key` and the core `deviceAuthorization` of the old agent approval, whose routes that make or use a key are closed until the clean-up release removes them, one `hooks.before` with the route allow-list, the refusal of any `Authorization` header and the other refusals, one `hooks.after` for sign-out, `databaseHooks` for the audit and, given `identityChanges` (`index.ts` and `cli.ts` pass agent access's), the identity changes that end agent connections, and `AuthHolder`, which rebuilds the instance when a setting it reads changes), `identity.ts` (the tracking of identity changes per call, with where Better Auth 1.7.19 can and cannot fail after it begins), `recovery.ts` (the CLI's documented password reset).
  - `oauth/`: agent access by approval, mounted by `index.ts` through `createApp`'s `agentOAuth`. `provider.ts` (`oidc-provider` 9.14.0 configured through its documented options: public clients, the built-in device client `adiutor-agent`, the registration rules validator, resource indicators for `/mcp` and `/api/v1`, every lifetime, the consent policy check), `store.ts` (its storage adapter on its own pool, hashed tokens and codes, atomic `consume`, the caps and the clean-up), `gate.ts` (the advisory lock gate, the generation, the issuer fingerprint), `access.ts` (`createAgentAccess`: the connection records, every end, the identity-change hooks, the approval, the per-call `checkToken` for PR 4, the owner's management, the sweep every 15 minutes), `routes.ts` (the hand-off of the library's exact paths with the host check and the limits, the protected resource documents, the approval API, `/api/v1/agents`, the flow headers on every address under `/connect/approve/`, the consent page that the built UI serves included), `issuer.ts`, `label.ts`, `limits.ts`, `skill.ts` (the agent skill served at `/agents/skill/`: an allowlist of its files, the address and the version filled in, LF line ends, only while agents are on and for an address of the safe shape; the folder comes through `agentOAuthMount`'s `skillDir`, no variable), `pages.ts` (the library's own pages through its documented sources: code, comparison, done, error; in the owner's language setting from the locale files' `agentPages`, light and dark by the system, no script, every value escaped, the library's forms as it hands them over), `signing-key.ts`, `sync-status.ts` (whether the sync is connected, for the morning read).
  - `agents/`: the policy core of agents connected by approval, built where `agentOAuth` is mounted (always in production). `policy.ts` is the closed table: every route of the app (method and path as Hono lists it) in `OPEN` (area, kind by effect, a description for agents ending with the data sentence, parameters) or `CLOSED` (with the reason), Better Auth's open paths in `CLOSED_AUTH_PATHS`, every MCP tool in `TOOLS` (or `CLOSED_TOOLS`), D4's `NEVER_OPEN`, the areas, the never list, `REVISION`, the endpoints listing, `SKILL_REVISION` and `updateSkillNotice` (the `update_skill` of REST `access`, from `X-Adiutor-Skill`). `policy.test.ts` is the exposure test: a new route or tool fails it until it is classified there. `channel.ts`: the agent gate's router for `/api/v1` (an agent request is one with an `Authorization` header; people's credentials removed; built from `OPEN` alone, with the owner's route code from `openRouteHandlers` in `http/api.ts`), the token check with its 401s and the invalid-token limit per address, the policy check (area 403, `X-Adiutor-Policy` and `X-Adiutor-Kind` 409), the slots, the deadline, the answer cap and the audit row of every call (`agent.api_call`, `agent.tool_call`), and the guard every MCP tool runs through. `rest.integration.test.ts` and `mcp.integration.test.ts` cover both channels over real HTTP.

  - `telegram/`: `api.ts` (Bot API client; a failure is `answer`, `not_sent`, `uncertain` or `aborted`), `html.ts` (Telegram HTML that escapes every value), `bot.ts` (long polling, one transaction per update), `runtime.ts` (owns the bot and the morning job; `reload` restarts them with the pair in effect, and sends sign-in codes), `texts.ts` (locale texts), `status.ts` (the status route's read).
  - `jobs/`: `morning.ts` (the 08:00 schedule and its durable runs in `job_runs`), `morning-message.ts` (the message, a pure function), `time.ts` (Asia/Jerusalem wall clock and number formats).
  - `testing/db.ts`: a migrated database per integration test file, and a movable clock. `testing/app.ts` (the app's core with Better Auth, the settings runtime and an idle Telegram service; agent keys and a signed-in owner for tests), `testing/browser.ts` (a cookie-jar browser with sign-up, enrolment and sign-in on Better Auth's routes), `testing/totp.ts` (a self-written RFC 6238 TOTP), `testing/passkey.ts` (a self-written software passkey: ES256, `none` attestation, its key pair new on every run). `testing/bot-api.ts`: a stand-in Telegram Bot API on `127.0.0.1` for tests (getUpdates with Telegram's offset rules, sendMessage recorded, failures on demand). `testing/agents.ts`: a live sync connection's record for tests of what reads it. `testing/oauth.ts`: agent access over real HTTP (the app on a Node server on `127.0.0.1`, whose address is the issuer), with the agent's and the owner's sides of each flow, and the agent channel's limits a test chooses. `testing/locks.ts`: `expectLinkLockFirst`, and `holdRow`, a row held `for update` so a call that changes it waits (a controlled slow call), with `waiting(n)` read from `pg_blocking_pids`.

## Commands

Run every script inside WSL from the repository. Node, pnpm, shellcheck and shfmt run in the toolchain container; the host needs Docker only.

- `scripts/verify.sh`: guards, Biome, types, unit tests, the agent skill's contract tests (`pnpm test:skill` in the toolchain, then the node version again in `SKILL_NODE_IMAGE`, a pinned Node 20 image), build, schema-versus-migration check, database tests against a disposable PostgreSQL 16 (`adiutor-verify`, `TEST_POSTGRES_IMAGE`; it stops unless the server reports 16), then the image with health, UID and hardening checks, then the end-to-end tests in the Playwright image against that container. After the build it checks `dist/web` for external assets and the mock (`scripts/lib/web-dist-check.sh`). `--guards-only` for the guards alone; `--changed [BASE]` runs guards only when every change is documentation; `--skip-e2e` skips the end-to-end tests.
- `scripts/local.sh build|up|start|down|status|logs|nuke`: the development stack (`adiutor-dev`) from the ignored `docker-compose-dev.yml`. Create it once with `cp docker/docker-compose-dev.example.yml docker-compose-dev.yml`. Serves `http://127.0.0.1:8090`; `ADIUTOR_PORT` changes the port and `ADIUTOR_PUBLIC_URL` the address the browser opens (a reverse proxy; both may be set in `.env.dev`). `up` and `start` generate the database password and the keys once into `<data dir>/stack.env` (0600) and refuse a database whose `stack.env` is missing.
- `scripts/try-pr.sh <number>|status|restore`: runs a pull request's head as the separate Compose project `adiutor-pr` (own PostgreSQL 16, generated keys in a 0600 file under `~/.cache/adiutor/try-pr`, an owner created through Better Auth's sign-up with a generated password, TOTP secret and backup codes in `owner.env` there, also 0600, Telegram off, invented fixtures made with the owner's session: no T3 threads, sync runs or security sources) on `http://pr.localhost:8091`; `ADIUTOR_PR_PORT` changes the port. Its server publishes no port: an nginx proxy (`proxy.conf` there) publishes `127.0.0.1:8091` and passes it only requests for the host `pr.localhost` (421 for any other), so the browser never sends it the cookies of `127.0.0.1`, where the development stack runs. Agents are not connected to a pull request stack: `connect` and the skill accept plain http only for `localhost` and `127.0.0.1`, and Node does not resolve `pr.localhost` (browsers and curl do). Never touches `adiutor-dev`. `restore` removes the stack, its data, image and worktree.
- Recovery on a running stack: `docker compose exec adiutor node dist/server/cli.js reset-password` (production) or `source scripts/lib/common.sh && dev_compose exec adiutor node dist/server/cli.js reset-password` (development). It runs Better Auth's documented reset: prints a new password once and ends every session; two-factor stays. Always `exec` in the running container, never `docker compose run` (agent access tells an identity change under way by its container).
- Releases: the **Release** workflow (Actions → Release → Run workflow on `main`, choose patch, minor or major; `dry_run` checks everything and publishes nothing) reuses the newest CI run of the commit on `main` when its latest attempt succeeded (waiting up to 30 minutes for one that still runs; it never falls back to an older green run) and runs the whole CI on the commit otherwise (`scripts/ci-result.sh` decides, and the workflow checks a reused run again with it right before `release.sh`), then `scripts/release.sh --target ghcr --bump <patch|minor|major> [--dry-run]`: release commit and tag, the image on GHCR (the version, then `:latest`) and the GitHub Release from the CHANGELOG section. A run that stopped halfway is finished by the next run (a new Run workflow, not "Re-run failed jobs"). Agents never release: they run the workflow only with `dry_run`, and `release.sh` only with `--dry-run`. `scripts/test-release.sh` (run by the guards) covers each way a run can stop, `scripts/test-ci-result.sh` which CI run counts, and `scripts/test-release-workflow.sh` which jobs and steps run on both CI paths with and without `dry_run` (both also run by the guards). Never deploys.
- A single tool in the toolchain: `source scripts/lib/common.sh && build_toolchain && in_toolchain "pnpm test"`.
- The agent skill's contract tests alone: `in_toolchain "pnpm test:skill"` (node and sh), or `node --test skill/test/contract.test.mjs` with any Node 20+ on the host (on Windows: node, ps and pwsh; `ADIUTOR_TEST_TMP` moves the temporary folder). `ADIUTOR_IMPLS=node,sh` picks the versions. CI runs them on Windows (node, ps, pwsh) and macOS (node, sh) in `.github/workflows/skill-contract.yml` when `skill/`, `src/sync/` or the workflow changes (owner's decision D11); Linux runs them in `verify.sh`.
- UI development: `in_toolchain "VITE_ADIUTOR_MOCK=1 pnpm dev:web"` serves the UI on the mock API (port 5173 in the container); without the flag `pnpm dev:web` proxies `/api` to the development stack.
- End-to-end tests against the development stack: `docker run --rm --ipc=host --network host --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD:/repo" -w /repo mcr.microsoft.com/playwright:v1.65.0-noble npx playwright test --config config/playwright.config.ts` (from a WSL clone; the tests create invented records and set the language to Hebrew). Pass `-e E2E_USERNAME -e E2E_PASSWORD` (the run refuses to start without a password), and `-e E2E_TOTP_SECRET` when that owner exists; on an empty database the first test creates the owner with them. Only `scripts/verify.sh`, whose stack is thrown away, lets global setup make a new password for the run.
- New migration after a schema change: `in_toolchain "pnpm db:generate --name <change>"`. `verify.sh` fails when the schema and the migrations disagree. A data-only change uses `pnpm db:generate --custom --name <change>` and is the only hand-written SQL.

Verify in proportion to the risk of the change, and report what ran and its result:

- **Documentation only** (`docs/`, `README.md`, `AGENTS.md`, `CHANGELOG.md`, `LICENSE`): `scripts/verify.sh --changed`, which then runs only the guards.
- **Anything else**: the full `scripts/verify.sh` before opening the pull request.

On a pull request, CI runs the guards, and `scripts/verify.sh --changed origin/main` unless only Markdown files, `docs/` or `LICENSE` changed; then it runs only the guards.

## Traps

- Node 25 and later no longer ship Corepack. Both Dockerfiles install it from npm at a pinned version (`corepack@0.36.0`) before `corepack enable`; the toolchain's `corepack prepare pnpm@...` must name the version of `packageManager`.
- The sync bundle (`build:sync`) targets `node24`, the Node of the owner's PC, while the server targets `node26`. Move the sync target only after the PC runs a newer Node (see `docs/sync.md`).

So the recovery command runs with `docker compose exec` in the server's container, never `docker compose run`.
- **Every route and MCP tool is classified for agents.** A new route of the app (any method, any prefix, middleware included as Hono lists it), a new path in Better Auth's `ALLOWED_PATHS` or `OTP_PATHS`, or a new MCP tool fails `agents/policy.test.ts` until it is put in `agents/policy.ts`: `OPEN` with area, kind by effect, description and parameters (and its handler in `openRouteHandlers`), or `CLOSED` with the reason. Opening one changes `REVISION`, so every skill reads the endpoints again (`409 policy_changed` once). `GET morning`, `inbox` and `archive` are closed until the owner decides; opening one is one table change.

## Repository policies

- Commit email is the GitHub noreply address.

## Product rules that code must enforce

- Agents may not delete items or projects and may not change a stage (they propose one). Only the owner, in the UI, does that.
- Every write goes through the services layer and writes an audit row in the same transaction. The one exception is the writes Better Auth does itself (sign-in, enrolment, sign-out), which fail closed instead (see Traps).
- The browser signs in with Better Auth: the password and TOTP, which is mandatory, or a passkey that verifies the person (owner's decision, 2026-11-15); a passkey can be added only once two-factor is on. Agents and the sync connect by approval (agent access, Settings, Agent access); agent keys are refused since the agent access release (D12). A session never stands in for an access token, and neither a key nor a token becomes a session.
- Text written by agents and the Telegram bot is checked for secrets and refused with `secret_suspected`.
- The bot serves only the configured owner chat and never answers another chat.
- The server never calls T3 or GitHub. Their data arrives through the sync tool on the owner's PC.
- The sync never overrides the owner: see "Agent and sync rules" in the foundation plan.
