# Adiutor HTTP API and MCP tools

Status: implemented in `src/server/http/`, `src/server/auth/`, `src/server/settings/` and `src/server/mcp/`; request bodies are the zod schemas in `src/shared/api.ts`. The UI, the Telegram bot and the sync tool build on this contract. Product rules are in [requirements.md](requirements.md); the sync rules in "Agent and sync rules" of [project-foundation.md](project-foundation.md).

## Conventions

- Base path `/api/v1`. JSON in and out (`Content-Type: application/json`). Bodies are limited to 512 KiB, sync snapshots to 16 MiB. The limits apply after authentication: a request without valid credentials is refused before the application reads its body.
- Success: `{"data": ...}`. Paged lists: `{"data": [...], "nextCursor": "..." | null}`; pass `cursor=<nextCursor>` for the next page. `201` for a created resource, `204` (no body) for a delete.
- Error: `{"error": {"code": "<code>", "message": "<for people>", ...details}}`. Branch on `code`, never on `message`.
- Times are ISO 8601 strings in UTC. Ids are UUIDs, except T3 thread and project ids (opaque strings, up to 200 characters). A UUID is accepted in any case and answered and recorded in lower case; an older audit row may hold one as the request spelled it.
- Codes (stage, status, type, severity, actor kind) are the English codes of `src/shared/enums.ts`. Labels come from the locale files.
- Unknown body fields are ignored. A path id that is not a UUID answers `not_found`.

## Authentication

Where agent access is mounted (not before the agent access release), agents use access tokens instead of keys: see "The agent channel" below. Until then, every route under `/api/v1` needs one of:

- **An agent key**: `Authorization: Bearer <key>`. An agent or the sync gets one through `adiutor connect` (below), after the owner approves it in the browser (Better Auth's `@better-auth/api-key` plugin): `adt_` and 64 letters, a name and an end date, stored as a SHA-256 hash. The server checks a key with the plugin's server-only `verifyApiKey`; a valid key acts as an agent. An agent may add `X-Adiutor-Agent: <name>` (letters, digits, space, `._:-`, up to 60 characters); the audit log then shows `agent:<name>`. A key never becomes a session.
- **The owner's browser session** (Better Auth, below), which acts as the owner. Better Auth has no option that requires two-factor, so Adiutor accepts a session only while the account has two-factor on (`user.twoFactorEnabled`); otherwise `403 totp_required`. Every request that is not `GET`, `HEAD` or `OPTIONS` must also send `X-Adiutor-Request: 1` and an `Origin` equal to the origin of `ADIUTOR_PUBLIC_URL`, or it is refused with `forbidden`. A session never stands in for a key where a key is required: the sync routes answer it `forbidden`, and `/mcp` accepts keys only.

A request with an `Authorization` header is an agent request: when both are present the key is used, and a wrong key is refused (`401`), never read as the cookie's session. The browser paths (`/api/v1`, `/api/setup/status`) give Better Auth's `getSession` the `Cookie` header alone, so a session token sent as `Authorization: Bearer` (which Better Auth's `bearer()` plugin accepts on its own routes) is never a session there. Failed keys count per client address: the socket's address, or, when the socket's peer is one of the proxies in `ADIUTOR_TRUSTED_PROXIES`, the address Better Auth reads from `X-Forwarded-For` (the first hop from the right that is not a trusted proxy; an IPv6 address by its /64). After 10 within a minute, every request with an `Authorization` header from that address answers `rate_limited` until the minute is over, a valid key included. A request without an `Authorization` header never counts and never waits: the owner's browser session keeps working whatever keys others send. Reading a session never extends it (`deferSessionRefresh`).

Rights: the owner may do everything. An agent may do everything else except delete, change a stage, decide proposals, create projects, rename or re-link a project, and read or change settings and suppressions (`forbidden`). An agent reads the audit log, but not the values of settings and suppressions in it (AuditEntry). Text written by an agent is checked for secrets (`secret_suspected`). There is no owner key: owner actions need the signed-in browser.

Writes record an audit row with the actor and a source: `ui` (browser session), `api` (agent key), `mcp`, `sync` (the sync routes), `telegram` (the bot, in process), `cli` (the recovery command on the server).

### Browser sign-in

One account, the owner's: a username, a password and a second factor, or a passkey alone (`@better-auth/passkey` 1.7.19), through Better Auth (`better-auth` 1.7.19) under `/api/auth`, used as it documents itself. The UI calls Better Auth's client; there is no Adiutor route in between. Sessions are cookies (`better-auth.session_token`, with the `__Secure-` prefix when `ADIUTOR_PUBLIC_URL` is `https`), `HttpOnly`, `SameSite=Lax`.

**Open routes.** A documented `hooks.before` admits only these route patterns over HTTP; every other path answers `404` (`/sign-in/email`, `/update-user`, `/request-password-reset`, `/reset-password/:token`, `/callback/:id`, `/api-key/update` and every route a later version adds). Server calls (`auth.api.*`) are not HTTP requests and are not limited by it.

- **Refused by Adiutor's hooks:** `trustDevice: true` on every route whose body accepts it (`400 TRUST_DEVICE_UNSUPPORTED`: there are no trusted devices); `/two-factor/enable` with a `method` other than `totp` (`400 TOTP_ONLY`: two-factor is set up with an authenticator app, and a Telegram code only signs in); `/api-key/*`, `GET /device`, `/device/approve` and `/device/deny` while the account has no two-factor (`403 TOTP_REQUIRED`); an `Authorization` header on any route but `/api-key/create` and `/revoke-session`, with or without a cookie (`403 AUTHORIZATION_NOT_ALLOWED`); `/revoke-session` with a bearer for another session than the bearer's own (`403 OWN_SESSION_ONLY`); a key `prefix` other than `adt_` (`400 INVALID_KEY_PREFIX`); a key created without a number `expiresIn` (`400 EXPIRES_IN_REQUIRED`: every key gets an end, which the plugin then holds to 1 to 365 days); a sign-up once the owner exists (`403 ALREADY_SET_UP`); adding a passkey while the account has no two-factor (`403 TOTP_REQUIRED`), when it has 20 already (`403 PASSKEY_LIMIT`; registrations that overlap in time can each pass this count), with a name outside 1 to 32 characters (`400 INVALID_PASSKEY_NAME`, also on rename), or with `createSession` (`400 PASSKEY_SESSION_UNSUPPORTED`: adding a passkey never signs in).
- **CSRF:** Better Auth's own: a `POST` that carries cookies must come from `ADIUTOR_PUBLIC_URL`'s origin (`403`), bodies must be JSON (`415` otherwise), and sign-up checks Fetch Metadata.
- **Rate limits:** Better Auth's limiter, stored in the database: every credential route (sign-up, sign-in, the two-factor routes, the password, `/passkey/verify-authentication` and `/passkey/verify-registration`) allows 5 requests per 5 minutes per address and route, the two passkey options routes 20 per 5 minutes, `/device/code` 10 per 10 minutes, `/device/token` 300 per 15 minutes (a code's whole lifetime of polling), `GET /device` 5 per 10 minutes (the plugin's own), everything else 100 a minute. A route's count restarts only after it has been quiet for a whole window. `adiutor connect` treats a 429 while polling as `slow_down`. The address is read from `X-Forwarded-For` behind the proxies in `ADIUTOR_TRUSTED_PROXIES` (see the condition in [deployment.md](deployment.md)). Two-factor also locks the account for 15 minutes after 10 wrong codes.
- **Server errors:** an unexpected failure inside Better Auth answers `500 internal_error`; the log holds only its class, SQLSTATE and code, never its message, query or values.
- **Audit**, from Better Auth's documented hooks, on Adiutor's own connection: `account.setup`, `session.sign_in` (`{stage: "password"}` for every session created after a password, also one the plugin turns into a challenge; `{stage: "second_factor", method}` after a code; `{stage: "passkey", method: "passkey"}` after a passkey), `account.passkey_add` (`{name}`, written after the browser's answer is verified and before the passkey is stored), `account.passkey_rename` and `account.passkey_delete` (`{name}`, the passkey's id), `account.totp_enable`, `account.totp_disable`, `account.password_change`, `account.password_reset`, `account.backup_codes_new`, `session.end` (one per session ended by sign out others, everywhere or the reset), `api_key.create` (source `api` when `adiutor connect` creates it), `api_key.delete`, `device.approve`, `device.deny`, `session.connect` (the session `/device/token` gives), and `session.sign_out` and `session.revoke` after the fact. A failing audit write refuses the change, except sign-out and `/revoke-session`, which are recorded after the fact and never refused. The row is not in the change's transaction (gap G5 in the foundation plan).

**Sign out after days without Adiutor open** (Settings, `sessionIdleDays`, 1 to 90, default 30): Better Auth's sliding `session.expiresIn` with `updateAge` 1 hour. Only the Better Auth client's own refresh extends a session: opening Adiutor, bringing its tab back to the front, coming back online, or a session change in another tab. Adiutor's polling never does. **Transport note:** The Better Auth client sends its session refresh (`POST /get-session`) without a body, `@hono/node-server` gives every POST a body stream, and better-call then requires a `Content-Type` (415). The `/api/auth` mount therefore passes a request without content (not GET or HEAD, `Content-Length: 0`, no `Transfer-Encoding`) with a null body (`withoutEmptyBody` in `src/server/app.ts`); everything else passes through unchanged. A transport fix, not a Better Auth change: remove it when upstream sends no body for empty requests. A change rebuilds the Better Auth instance at once; a shorter value does not shorten browsers already signed in until their time left falls under it (use sign out everywhere).

### Agent approval (`adiutor connect`)

The clients on `main` no longer use this flow: the agent skill and the sync connect through agent access by approval (below), which works only against the agent access release. The routes stay until that release closes them.

An agent or the sync of an earlier release gets its key in the browser: Better Auth's core `deviceAuthorization` plugin, its `bearer()` plugin and the api-key plugin, used as documented. `adiutor connect` is a subcommand of the sync bundle (see [sync.md](sync.md)).

1. The CLI sends `POST /api/auth/device/code {client_id: "adiutor-connect"}` (the only client id `validateClient` accepts) and gets `device_code`, `user_code` (8 letters and digits), `verification_uri` (`<public URL>/connect/device`), `verification_uri_complete`, `expires_in` 600 and `interval` 5. It prints the link and the code and opens the browser.
2. The owner opens `/connect/device?user_code=…`, signs in when needed, and the page calls `GET /device?user_code=…`, which claims the code for this session. It shows the code to compare, then Allow (`POST /device/approve {userCode}`) or Deny (`POST /device/deny`). A code is answered once; an expired one answers `400 expired_token`.
3. The CLI polls `POST /device/token {grant_type: "urn:ietf:params:oauth:grant-type:device_code", device_code, client_id}` every `interval` seconds: `authorization_pending`, `slow_down` (it then waits 5 seconds longer), `access_denied`, `expired_token`, or `{access_token, token_type: "Bearer", expires_in}`. An approved code is redeemed once, also when polls race.
4. The access token is a full owner session (gap G-B in the foundation plan), with `User-Agent: adiutor-connect`, lasting what every session lasts (the idle days). The CLI sends it as `Authorization: Bearer` to `POST /api-key/create {name, expiresIn}`, then, whatever happened, to `POST /revoke-session {token}` with its own token. Adiutor's hook lets the header reach those two routes only.
5. The key goes to the sync's env file, or into Claude Code or Codex through their own `mcp add` commands; it is printed once only when a client's command is missing or fails. Settings, Agent access lists it; Disconnect deletes it and its next request is refused. `GET /api-key/list` answers at most 100 keys (the database adapter's default; `total` counts those), so Disconnect all lists and deletes again until a list comes back empty, and says how many are left when it stops early.

**Gap G10, accepted by the owner (2026-11-02)** (foundation plan): `bearer()` adds a `set-auth-token` header to every answer that sets the session cookie (sign-in), holding the signed cookie value and readable by page script; sent back as the cookie, it is the owner's session on every route. The Content-Security-Policy (`script-src 'self'`) is what keeps other scripts out of the page.

The agent skill of an earlier release was a second client of this flow; the skill on `main` is an OAuth client of the agent channel (below, and [SKILL.md](../skill/adiutor/SKILL.md)).

Name and days come from the command, not from the approval page (gap G-A). A signed-in owner session can still call `/api-key/create` itself: the UI has no button for it.

### Recovery

`node dist/server/cli.js reset-password`, run in the container on the server, resets the password through Better Auth's documented flow (`requestPasswordReset` with a local sender, then `resetPassword`, as server calls): a new random password printed once, every session ended, two-factor and passkeys unchanged. Audit rows `session.end` and `account.password_reset` (actor `system`, label `cli`, source `cli`). The reset routes are closed over HTTP. Without the authenticator, the backup codes saved at enrolment are the way in.

## Shapes

Fields are always present; `null` when unset.

- **Item**: `id, projectId (null: inbox), type, status, title, body, severity (security only), goalId, version, statusSetBy, statusSetAt, createdBy, imported, createdAt, updatedAt, closedAt (set exactly when status is done or not_relevant)`.
- **ItemSummary**: `id, projectId, projectName, type, status, title, severity, goalId, version, statusSetBy, createdAt, updatedAt, closedAt`.
- **Project**: `id, name, slug, t3ProjectId, githubRepo ("owner/name"), stage (null until the owner sets one), whereWeAre, openIssuesCount, openIssuesAsOf, createdAt, updatedAt`.
- **GoalProgress**: `id, text, createdAt, done, total`: `done` items linked to the current goal out of `total` items linked to it.
- **Goal**: `id, projectId, text, createdAt, closedAt`.
- **ThreadLink**: `id, itemId, threadId, t3ProjectId, title, lastStatus (T3's status), settled, lastActivityAt, linkedAt`.
- **Comment**: `id, itemId, authorKind, authorLabel, text, threadId, noteId, createdAt`. `noteId`: the note this comment points to (set when the Telegram bot moved the item's text into a note; null when that note was deleted).
- **Note**: `id, projectId (null: a general note), title, body (Markdown, up to 100,000 characters), version, createdBy, createdByLabel, updatedBy, updatedByLabel, createdAt, updatedAt`.
- **NoteSummary**: a Note without `body`, with `excerpt`: the start of the body as plain text on one line (Markdown marks dropped, link text kept), up to 240 characters.
- **NoteVersion**: `id, noteId, version, title, body, projectId, authorKind, authorLabel, restoredFrom (the version it restored, or null), createdAt`. `projectId` is the project the note was in; that project may have been deleted since.
- **NoteVersionSummary**: `version, title, projectId, authorKind, authorLabel, restoredFrom, createdAt, bodyLength`.
- **StageProposal**: `id, projectId, proposedStage, reason, authorKind, authorLabel, state (open, accepted, rejected), createdAt, decidedAt`.
- **SecuritySource**: `id, projectId, family (dependabot, code_scanning, secret_scanning, overview), coverage (enabled, not_enabled, no_access, error, unknown), critical, high, medium, low, asOf, updatedAt`.
- **SyncRun**: `id, kind (t3, security), startedAt, finishedAt, outcome (succeeded, partial, failed; null while running), counts {name: number}, errors [{record, code}]`.
- **SyncResult**: `runId, outcome, counts, errors`.
- **Suppression**: `id, kind (thread, project), externalId, label (what was deleted), createdAt`.
- **Settings**: `id, closedItemDays (1 to 365, default 7), dateFormat, timeFormat, language (he, en), sessionIdleDays (1 to 90, default 30), otpViaTelegram (default false), updatedAt, telegram, privateDomains`. `telegram`: `{botToken: {set, readable, locked, variable}, chatId: {value, locked, variable}, state: "off" | "incomplete" | "on", missing: ("botToken" | "chatId")[]}`: the bot token is never returned; `readable: false` means it was stored with a settings key that is no longer listed. `privateDomains`: `{value: string[], locked, variable}`. A field an environment variable sets is `locked` and names it in `variable`. The formats the UI offers are in `src/shared/datetime-formats.ts`: `dateFormat` is `dd/MM/yyyy` (default), `MM/dd/yyyy`, `dd.MM.yyyy`, `yyyy-MM-dd` or `browser`; `timeFormat` is `HH:mm` (default), `h:mm a` or `browser`. The morning message writes `browser`, and any value not offered, as the default numeric date and the 24-hour clock.
- **AuditEntry**: `id (number), at, actorKind, actorLabel, action, entityType, entityId, before, after, source`, and `redactedFields` on a redacted row. Only the owner reads every row whole. Any other reader (an agent key, the sync) gets the rows of `settings` and `suppression`, which only the owner may read, with `before: null`, `after: null` and `redactedFields`: the names of the fields whose values differ between before and after, sorted (every field of a suppression created or removed; for settings, the columns that changed, `updatedAt` when it changed, and `telegramBotTokenChange` when the bot token was replaced or removed). The bot token itself is never in a row, for any reader: settings rows hold it only as `set` or `unset`. Actions: `item.create|update|delete`, `comment.create`, `note.create|update|restore|delete`, `thread.link|update|move|unlink`, `project.create|update|delete`, `goal.create|close`, `proposal.create|update|accept|reject`, `security.update`, `suppression.create|delete`, `settings.update`, `account.setup|totp_enable|totp_disable|password_change|password_reset|backup_codes_new|passkey_add|passkey_rename|passkey_delete`, `session.sign_in|sign_out|end|connect|revoke`, `api_key.create|delete`, `device.approve|deny`, `telegram.test_message`. The list is `AUDIT_ACTIONS` in `src/shared/enums.ts`; every action has a label in both locale files. Older rows may also hold `device.pair|revoke|revoke_all`, `session.end_others|end_all|sweep` and `auth.repair`. Comment, thread, goal and proposal entries carry the entity of their item (`item`) or project (`project`), so an item's history includes them.

## Routes

"Owner" routes answer `forbidden` to the agent token.

### Session and the overview

| Method and path | Who     | Body or query   | Answer                                                                                                                                                                                                                      |
| --------------- | ------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /session`  | any     |                 | `{actor: {kind, label}, via: "token"\|"session", expiresAt}`. `expiresAt` (a session only): when it ends unless the Better Auth client refreshes it first                                                                   |
| `GET /morning`  | any     | `since?` (time) | Morning (below). `since` is the owner's previous visit in any browser unless the query gives one                                                                                                                            |
| `POST /visits`  | browser | `{at?}` (time)  | `201 {at, previous}`. Call after the overview was shown, with that read's `now`; recorded one minute before `at`, or before now when `at` is missing or later than the server's clock (see below). `forbidden` with a token |

"browser" routes need the owner's browser session (`forbidden` with a key). The password, the browsers list and signing out are Better Auth's routes (above).

**Last visit:** belongs to the owner's account, not to a browser (owner's decision, 2026-11-13). A visit recorded in one browser is the previous visit that the next overview in any browser or device counts from. Adiutor sets no cookie of its own.

**Morning**:

```text
{
  now, since,
  waiting: [ {kind: "item", at, item: ItemSummary}            // status waiting_on_you
           | {kind: "stage_proposal", at, proposal: {id, projectId, projectName, currentStage,
                                                      proposedStage, reason, authorKind, authorLabel, createdAt}} ],
  new: [ {change: "created" | "updated", item: ItemSummary} ],
  security: [ {projectId, projectName, stage, critical, high, alerts: {critical, high},
               items: {critical, high}, asOf, stale} ],
  agentUpdates: [ {projectId, projectName, generalNotes, updates: [
      {kind: "comment", at, itemId, itemTitle, actorKind, actorLabel, text}
    | {kind: "status",  at, itemId, itemTitle, actorKind, actorLabel, from, to}
    | {kind: "note",    at, noteId, noteTitle, actorKind, actorLabel, change: "created" | "updated"} ]} ],
  projects: [ {id, name, slug, stage, goal: GoalProgress | null, whereWeAre, openItems,
               openIssues, openIssuesAsOf, repo} ],
  inboxCount,
  sync: {lastSuccessAt, stale, lastPartialAt, securityLastSuccessAt}
}
```

- `now`: the server's time when this read started. A visit recorded with it marks nothing newer than what this read showed as seen. The visit is stored one minute before `now`: a write whose transaction was still open during the read has a time before `now`, so it must be less than a minute before `now` to count as new on the next visit. The server's transactions are a few statements each, every statement ends after 15 seconds and a transaction left idle ends after 15 seconds, so in practice it is. PostgreSQL 16 has no limit on a whole transaction, so this bound is practical, not hard: a write that commits more than a minute after it took its time could show as not new. Items written in that minute may show as new twice.
- `since`: the `since` query when given; else the owner's latest recorded visit in any browser; 24 hours before now when there is none. Token callers get the same boundary. The UI keeps the `since` of the page's first read and passes it on every refresh, so "new since your last visit" stays stable while the page is open; a visit in another browser counts from the next time the overview opens.
- Items shown anywhere in the view: open items, and closed ones closed within `closedItemDays`. Older closed items are only in the archive.
- `new`: created after `since` (`change: "created"`, except items imported by the first sync run) or changed after `since` and after their creation (`"updated"`). Newest first.
- `security`: one line per project with something to say. `critical` counts in every project, `high` only at stage `production` (0 elsewhere). Counts come from enabled `dependabot`, `code_scanning` and `secret_scanning` sources plus open `security` items of the project. `asOf` is the oldest as-of time of the project's enabled sources (null when it has none); `stale` is true when that time is unknown or older than 26 hours.
- `agentUpdates`: comments, status changes and note versions by agents and the sync after `since`, grouped by project, groups and updates newest first, at most 300 of each kind. `projectId: null` is the inbox's items, or the notes without a project when `generalNotes` is true. A note's events come from its versions, so a later edit by the owner does not hide them; `noteTitle` is the note's title now, and a deleted note's events are gone.
- `projects`: projects with at least one open item, by name.
- `sync.lastSuccessAt`: when the last complete T3 run (`succeeded`) finished; a `partial` run may have missed whole projects, so it never counts as fresh. `sync.lastPartialAt`: when the latest `partial` T3 run finished, only when it is later than `lastSuccessAt` (else null). `sync.securityLastSuccessAt`: the latest security run that was `succeeded` or `partial`.
- `sync.stale`: no complete T3 sync, or the last one finished more than 26 hours ago.

### T3 threads and sync

| Method and path       | Who   | Body                                                                                                           | Answer                                                                      |
| --------------------- | ----- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `POST /threads/start` | any   | `{threadId, parentThreadId (required, null for a top-level thread), title, projectId?, t3ProjectId?, itemId?}` | `{item: Item, created, linked}`: `201` when an item was created, else `200` |
| `POST /sync/t3`       | token | T3 snapshot (below)                                                                                            | `SyncResult`                                                                |
| `POST /sync/security` | token | Security snapshot (below)                                                                                      | `SyncResult`                                                                |
| `GET /sync/runs`      | any   | `limit?` (default 20)                                                                                          | `SyncRun[]`, newest first                                                   |

**Start of thread**, in one transaction: refuses `not_top_level` when `parentThreadId` is set; returns the item already linked to `threadId` (also on a retry or a race); otherwise links `itemId`, or creates a `task` in `projectId`, or in the project whose `t3ProjectId` matches, or in the inbox. The item is set `in_progress` (a closed item reopens). `suppressed` when the owner deleted this thread's item; `conflict` when `itemId` differs from the item the thread is linked to.

**Sync routes** accept a bearer token only (a browser session is `forbidden`). Changes are recorded with actor kind `sync`. Per-record failures are collected in `errors` (`record` is `project:<t3ProjectId>`, `thread:<threadId>`, `item:<id>`, `repo:<owner/name>`, `threads:<t3ProjectId>` or `snapshot`; `code` is an error code, or `threads_not_read` or `time_in_future`) and never stop the run; `outcome` is `partial` when some failed or the snapshot lists `failedProjects`, `failed` when all failed.

**Times later than the server's clock** plus 5 minutes are refused, so a record dated in the future cannot stand against the honest snapshots after it (the newer record always wins). A `collectedAt` beyond that refuses the whole snapshot: nothing of it is applied, the run is recorded as `failed` with `{record: "snapshot", code: "time_in_future"}`, and the answer is `400 validation_failed`. A thread whose `updatedAt` or `settledAt` is beyond it, or a repository whose `issuesAsOf` or any family's `asOf` is, is refused alone (`{record: "thread:<threadId>" | "repo:<owner/name>", code: "time_in_future"}`, counted as a failed record) and the rest of the run goes on. The bound is the server's clock, not `collectedAt`: the sync tool takes `collectedAt` before it reads the threads, so a thread's `updatedAt` may be later. Records already stored are kept as they are.

T3 snapshot, a full read of every top-level and child thread of every T3 project, never a delta:

```text
{
  collectedAt,
  projects: [ {t3ProjectId, title, repo?: "owner/name" | null} ],
  threads:  [ {threadId, t3ProjectId | null, title, status, settled, settledAt?: time | null,
               parentThreadId?: id | null, updatedAt} ],
  failedProjects?: [ t3ProjectId ]
}
```

- `failedProjects`: T3 projects whose threads the sync tool could not read in this run, or read only in part (invalid thread records). Each is recorded in `errors` as `{record: "threads:<t3ProjectId>", code: "threads_not_read"}`, the run is `partial`, and no item of those projects (by its project or by a link's `t3ProjectId`) is decided in this run (`counts.itemsNotDecided`).

- Projects: created by `t3ProjectId` with the redacted title as name, `stage: null` and the repository; an existing project keeps its name and only gets a repository when it has none; a suppressed project id is skipped.
- A thread with a `parentThreadId` never gets an item. When it is linked, the link moves to its top-level thread (the parent's parent, as far as the snapshot knows): deleted when that thread has its own link, re-pointed otherwise. When that thread has no link of its own and the owner suppressed it, or its project (when the snapshot names the thread and its project), the child's link stays as it is (`counts.childLinksSuppressed`). When that top-level thread is not in the snapshot or was refused for a time in the future, the link is re-pointed without its data.
- A top-level thread without an item and without a suppression (of the thread or its project) gets a `task` titled from the redacted thread title, in the mapped project or the inbox: when unsettled, whatever its age (`waiting` → `waiting_on_you`, otherwise `in_progress`); when settled, only if it settled (`settledAt`, else `updatedAt`) at most 7 days before `collectedAt` (status `done`). Items created by the first successful run are `imported`.
- Every link is refreshed (title, status, settled, `updatedAt` as last activity) when the record's `updatedAt` is newer than the stored last activity (an older or equal record is ignored, so snapshots applied out of order never roll back), then every item with a link is decided over all its links: any `running`, `starting`, `queued` or `preparing` → `in_progress`; otherwise any `waiting` → `waiting_on_you`; otherwise all settled → `done`; otherwise no change. The sync never moves an item out of `done` or `not_relevant`, never sets `done` on `future` or `todo`, and leaves a status the owner set at or after the threads' latest activity. Each change is a compare-and-set on the version read in that run; a changed or deleted item is skipped (`counts.itemsSkipped`) and decided again next run.
- Counts: `projectsCreated`, `projectsUpdated`, `projectsSuppressed`, `childLinksFolded`, `childLinksSuppressed`, `threadsUpdated`, `threadsSuppressed`, `threadsTooOld`, `itemsCreated`, `itemsUpdated`, `itemsSkipped`, `itemsNotDecided` (only the non-zero ones are present).

Security snapshot, from the `overview` collector:

```text
{
  collectedAt,
  repos: [ {repo: "owner/name", openIssues: n | null, issuesAsOf: time | null,
            families: [ {family, coverage, counts: {critical, high, medium, low}, asOf: time | null} ]} ]
}
```

Each repository is matched to every project whose `githubRepo` equals it, ignoring case (`counts.reposUnmatched` otherwise). The project's open Issues count and its time are replaced; each listed family is upserted; families not listed keep their last values. A family, or the open Issues count, whose as-of time is older than the stored one is ignored; a repository with a time later than the server's clock allows is refused whole (above). `asOf` is the source's last success, not the sync time. An unchanged project writes nothing.

### Telegram

The bot and the morning message run inside the server, never through this API. They are on only while a bot token and a chat id are both in effect: each is set in Settings, or by `ADIUTOR_TELEGRAM_BOT_TOKEN` and `ADIUTOR_TELEGRAM_CHAT_ID`, which override the stored value per field. With one of them the state is `incomplete` and the bot stays off. A save restarts them; the morning message still goes out at most once a day.

**TelegramStatus**:

```text
{
  configured,          // a bot token and a chat id are in effect, and the bot runs
  polling,             // the bot's latest getUpdates call succeeded (false when not configured)
  lastUpdateAt,        // when the bot last recorded an update from any chat, or null
  lastMorning: {localDate: "YYYY-MM-DD", state, at} | null   // the latest morning run
}
```

- `lastMorning.state`: `sending` (in progress), `sent`, `failed` (Telegram refused it with a 4xx answer, or there was no connection; retried every 30 seconds until 11:00), `unknown` (it may have gone out: a timeout, a dropped connection, a 5xx or an answer that is not Telegram's, or a restart during the send; never resent) or `skipped` (11:00 passed without a send). `at` is the time of the latest state change.
- **Quick add**: plain text from the owner's chat becomes an inbox item exactly like `POST /capture` (type `idea`, status `future`), created by actor kind `bot` with audit source `telegram`. The bot answers with a link to `<ADIUTOR_PUBLIC_URL>/items/<id>` and a **Make it a note** button. Text that looks like a secret is refused as agent text is, and the bot answers that nothing was saved without repeating the text. `/start`, `/help` and other commands answer with a help text; photos and other non-text messages with a short note. Other chats get no answer.
- **Make it a note**: the button's data is `note:<update_id of the capture>`; the server stored the item with that update, so a button only ever moves the item its message reported. The bot asks Telegram for `message` and `callback_query` updates. A press counts only from the owner, in the owner's chat, and not from a bot; any other press gets no answer. In one transaction that first takes the link structure lock (as an item delete does), it moves the item when it is still as captured (in the inbox, status `future`, version 1): a general note with the item's title and text (actor `bot`), the item closed as `not_relevant`, and a comment on it in the owner's language whose `noteId` is the note. The bot never deletes the item. The press's own update records `note_created`, `ignored` (moved already) or `refused` (the item changed since, a button that names no capture, or text that now looks like a secret). After the commit, each on its own, the bot answers the press with a short text, takes the button off unless the button names no capture, and on a move sends a link to `<ADIUTOR_PUBLIC_URL>/notes/<id>`. A failure there is logged and never repeats the move, and a redelivered press is a repeated update that does nothing.
- **Morning message**: 08:00 Asia/Jerusalem, Sunday to Friday, in the language of the settings, built from the overview's read (above) with `since` set to the owner's last visit in any browser or the last morning message, whichever is later, and 24 hours back when there is neither. Deep links: `<ADIUTOR_PUBLIC_URL>/` and `<ADIUTOR_PUBLIC_URL>/items/<id>`.
- **Test message**: `POST /telegram/test-message` (Settings, "Send a test morning message") builds the same message the job would send now and sends it to the owner's chat at once. It never reads or writes `job_runs`, so the 08:00 message still goes out, and it records two audit rows (action `telegram.test_message`): `after: {state: "sending"}`, committed before the send, then `after: {state, code?}` with `sent`, `failed` or `uncertain` and the failure code. Not retried.

## Agent access by approval (not reachable until the agent access release)

The authorization server for agents (`oidc-provider` 9.14.0, `src/server/oauth/`) and its routes exist only where `createApp` is given `agentOAuth`. Production does not pass it until the agent access release: none of these routes is reachable, and agents keep using agent keys as above. Everything below answers `404` while agents are off (`agents_enabled`) or while `ADIUTOR_PUBLIC_URL` is not an issuer agents may use: https, or http on exactly `localhost`, `127.0.0.1` or `[::1]`, written as a browser spells its origin (`issuerProblem`: `invalid`, `not_origin`, `plain_http`, `spelling`).

The issuer is the public URL's origin. The two resources are `<issuer>/mcp` (areas `read`, `write`) and `<issuer>/api/v1` (areas `read`, `write`, `sync`); the areas are the OAuth scopes. A token is for one resource, and a request that names both is refused (`invalid_target`).

| Method and path                                    | What                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `GET /.well-known/oauth-protected-resource[/mcp]`  | RFC 9728 for `/mcp`: `{resource, authorization_servers: [issuer], scopes_supported: ["read", "write"], bearer_methods_supported: ["header"], resource_name}`, `Cache-Control: no-store`                                                                                                                                                                                                             |

A device poll whose code is waiting or approved is not counted.

The code page, its comparison, the done page and the error page are in the owner's language setting (right to left in Hebrew), light or dark as the system asks; the page the library shows for a link that carries `user_code` (it posts the code on by itself) is the library's own, in English. Every answer of the flow (the library's pages and redirects, the consent page `/connect/approve/<uid>` that the built UI serves, and the approval API below) carries `Cache-Control: no-store`, `X-Frame-Options: DENY`, `frame-ancestors 'none'` and `Referrer-Policy: no-referrer`; the consent page keeps the UI's whole Content-Security-Policy.

**The approval API** (for the consent page; the owner's signed-in browser with two-factor only: a request with `Authorization` or `X-Api-Key` gets `403`, one without a session `401`; without agent access mounted both answer `404 not_found` like any unknown address, never the UI's page; errors are `{error, message}` with the stable codes `unauthorized`, `totp_required`, `forbidden`, `not_configured`, `gone`, `validation_failed` and `unsupported_media_type`):

Answered once; a second answer, or one while an identity change is under way, is `410`. Answers `{outcome: "approved" | "denied", redirectTo}`: where the browser goes next (back to the agent, or the code flow's done page).

**The owner's connections and settings** (`/api/v1/agents`, owner only, the browser contract above). Settings, Agent access reads `GET /api/v1/agents/settings` first: an Adiutor without agent access answers it `404 not_found`, and the page then shows the agent keys above instead:

A connection ends for good, with its reason (`agent.end`, `agent.end_all` in the activity log): the owner disconnects it or all, agents turned off, no real API or MCP call for the idle days (a refresh does not count), a spent refresh token or code came back, the agent revoked a token, the owner's password was changed or reset or two-factor turned off, or the public URL changed.

## The agent channel (not reachable until the agent access release)

Where agent access is mounted, agents connected by approval call `/api/v1` and `/mcp` with an OAuth access token through one policy core (`src/server/agents/`). Production does not mount it until the agent access release: until then every request to `/api/v1` and `/mcp` is answered as described above (agent keys and the owner's browser session), and nothing in this section is reachable.

**Who is an agent.** A request to `/api/v1` with an `Authorization` header, of any scheme, and every request to `/mcp`. It needs exactly one `Authorization: Bearer <access token>` made for that resource (`<issuer>/api/v1` or `<issuer>/mcp`): a token for the other resource, an agent key or a Better Auth session token is not valid there (`401 invalid_token`). The `Cookie` and `X-Api-Key` headers of an agent request are removed before anything reads them, so a bearer next to the owner's cookie never reaches a route through the cookie and never keeps a session alive. The owner's browser (a cookie and no `Authorization`) keeps the contract above, with `{error: {code, message}}`. A Bearer token anywhere else than `/api/v1`, `/mcp`, Better Auth's `/api/auth/api-key/create` and `/api/auth/revoke-session` (its own allow-list) and the approval API (`/connect/approve/<uid>/details` and `/decision`, which refuses it itself) is refused with `403 forbidden` before any route runs: the health check, the authorization server, its documents and every page of the UI included.

**The closed table.** Every route of the app is open to agents in one area with its kind, or closed with the reason, in `src/server/agents/policy.ts`; `src/server/agents/policy.test.ts` fails on a route or MCP tool in neither. The agent router of `/api/v1` holds the open routes alone, so a path it has no route for is closed: `403 forbidden`. Open routes (the same code as the owner's routes):

| Area    | Kind   | Routes                                                                                                                                                                                                                                                                                                                                                                  |
| ------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| any     | `read` | `GET /api/v1/agent/access`, `GET /api/v1/agent/endpoints[?area=]`                                                                                                                                                                                                                                                                                                       |
| `read`  | `read` | `GET /api/v1/items`, `GET /api/v1/items/{id}`, `GET /api/v1/projects`, `GET /api/v1/notes`, `GET /api/v1/notes/{id}`                                                                                                                                                                                                                                                    |
| `write` | `act`  | `POST /api/v1/threads/start`, `POST /api/v1/items`, `PATCH /api/v1/items/{id}`, `POST /api/v1/items/{id}/comments`, `POST /api/v1/items/{id}/threads`, `POST /api/v1/capture`, `PATCH /api/v1/projects/{id}` (`whereWeAre` and `goal`; any other field `403 forbidden`), `POST /api/v1/projects/{id}/stage-proposals`, `POST /api/v1/notes`, `PATCH /api/v1/notes/{id}` |
| `sync`  | `act`  | `POST /api/v1/sync/t3`, `POST /api/v1/sync/security` (REST only, never on MCP)                                                                                                                                                                                                                                                                                          |

Everything else is closed, among them `GET /morning`, `/inbox` and `/archive` (not used by agents; the owner has not decided yet), `GET /projects/{id}`, `/audit`, `/sync/runs`, `/session`, `/visits`, note versions and restore, settings, suppressions, Telegram, stage-proposal decisions, every delete, project create, `/api/v1/agents/*`, the OAuth and approval routes and Better Auth's routes.

**Before any route code runs**, in this order:

1. The token. `401` with `WWW-Authenticate: Bearer resource_metadata="<issuer>/.well-known/oauth-protected-resource/api/v1", error="invalid_token"` (`.../mcp` on `/mcp`) and `Access-Control-Expose-Headers: WWW-Authenticate`, body `{"error":"invalid_token","message":"The token is not valid here, or the connection has ended."}`. A missing, empty, malformed, mixed or repeated `Authorization` header is `401` `error="invalid_request"` with `{"error":"invalid_request",...}`; on `/mcp` a request without one is `401` with the metadata and no `error`. After 20 invalid tokens from one client address within a minute, its requests with a token, valid ones too, are `429 {"error":"rate_limited",...}` with `Retry-After` until the minute is over, logged and audited (`agent.blocked`) once per window. Tokens are counted before they are checked (a valid one is given back), so requests sent at once cannot pass the limit together.
2. A free slot of the connection: `429` with exactly `{"error":"busy","message":"This connection runs too many calls at once. Nothing was sent; try again."}`. The checks below run in the slot, so each of their refusals is recorded like any call.
3. The route and the area. `403 {"error":"forbidden",...}` for a closed route; `403 {"error":"area_not_granted","message":...,"area":"<area>"}` for an open route of an area the connection was not granted.
4. The policy revision and the declared kind (REST only; `access` and `endpoints` are exempt): every call sends `X-Adiutor-Policy: <revision>` (from `endpoints`) and `X-Adiutor-Kind: read|act` (the kind the list gives the call). A missing, different, repeated or unknown value, or a kind other than the one of the route the router picked, is `409` with exactly `{"error":"policy_changed","message":"Adiutor's calls changed, or this path names a different call than the list says, or this skill is older than Adiutor. Nothing ran. Run \`adiutor endpoints\` and take the path from it; if this keeps happening, install the skill again from <issuer>/agents/skill/."}`: a copy older than these headers never reads `update_skill`, so the refusal names where to install the skill again (the client reads only `error`).

These are the only `401`, `429` and `409 policy_changed` an agent gets; the client may send a call again only after one of them. No route answers them: a route's own `401` reaches the agent as `403` and its own `429` as `409`, each with its own code (no open route answers either today). `409 version_conflict` (a stale `version` on `PATCH items/{id}` or `notes/{id}`) keeps its status and code: it is not the reserved marker, the client passes it back as it is, and a versioned `PATCH` sent once more can never apply twice (the skill's exception D10).

**Errors** are `{"error": "<code>", "message": "<text>", ...details}` (D9), with the codes of the error table above (`validation_failed`, `not_found`, `forbidden`, `version_conflict` with `currentVersion`, `secret_suspected` with `rule` and `field`, `not_top_level`, `suppressed`, `conflict`, `internal_error`) and the channel's own: `invalid_token`, `invalid_request`, `unauthorized` (`/mcp` without a token), `rate_limited`, `area_not_granted`, `policy_changed`, `busy`, `too_large` (`413`), `answer_too_large` (`422`), `outcome_unknown` (`504`) and `connection_ended` (MCP). Messages never repeat a request value. A refusal before anything changed is a `4xx`; a `5xx` means the outcome may be unknown.

**Limits**, shared by REST and MCP:

- Bodies: 512 KiB, sync snapshots 16 MiB: `413 too_large` before the route reads the body (on `/mcp`, the SDK's own `maxRequestBodySize`).
- Answers: 8 MiB. Measured on a database shaped like heavy use (60 projects, 1,200 items with 2 KB bodies, 300 notes of 5 KB): a page of 200 items 0.10 MiB, 200 notes 0.15 MiB, 60 projects 0.08 MiB, a 100,000-character note 0.13 MiB, an item with 60 comments and 40 changes 0.73 MiB, and the largest item the limits allow in practice (a 20,000-character body, 200 comments of 2,000 characters, the last 100 changes of the whole body) 5.79 MiB. The answers of `act` routes echo one record and stay far below the cap. An item's comments have no count limit, so an item beyond that is answered `422 answer_too_large` ("Ask for less"); an `act` route over the cap would add "The action ran".
- Time: 60 seconds. A call past it is answered `504` with exactly `{"error":"outcome_unknown","message":"The call took too long, and it may still be running. Read the state it was to change before you try again."}`; it goes on running in its slot.
- Calls at once: 3 per connection and 6 in total, REST and MCP together (the standard's 2 and 4, raised because one connection is shared by every agent install of the owner's computer user, who runs several T3 threads at once; 6 leaves the app's pool of 10 room for the owner's browser, the bot and the sweep).

**Use.** A call that passed the policy check and the body limit and ran its route (REST) or tool (MCP) counts as use for the idle rule. `access`, `endpoints`, MCP's `initialize` and `tools/list`, `get_access`, and every refused call do not: MCP clients list tools by themselves at every start, so counting them would keep a connection nobody uses alive.

**Audit.** Every agent call, reads included, leaves exactly one row, inside its slot, never changing the answer: `agent.api_call` (source `api`) or `agent.tool_call` (source `mcp`), actor `agent:<X-Adiutor-Agent>` or `agent:<the connection's name>`, entity the connection, and `after: {name, route or tool, method, kind, outcome, status or refusal}`. `outcome` is `ok`, `error` (a 4xx or 5xx of the route, an answer over the cap, a sync push answered 200 whose run `failed` or was `partial`), `denied` (a refusal of the policy core) or `unknown` (past the deadline, or the client already gone when the row is written). The row is written before the answer goes out; the answer waits at most 5 seconds for it, and the write goes on in the call's slot, which comes back only once the row is written or failed. `busy`, the one refusal without a slot, is recorded once per connection and minute. The mount's `drain` waits for the audit writes still running, for shutdown before the database closes. A call refused for its token has no connection and no row.

**`GET /api/v1/agent/access`** (and the MCP tool `get_access`) answers, not wrapped in `data`: `{account, name, connection: {via, resource, approvedAt}, areas: [{area, kinds, sentence}], notGranted: [...], never: [...], ends: {rule, lastUsedAt, endsAt}, version}`, and on REST `update_skill` when the skill is older than this Adiutor. The skill sends `X-Adiutor-Skill` on every call: a copy Adiutor served sends the version it filled in (the first 12 hex digits of SHA-256 over each served file's name, length and content), a copy from Git sends `r<SKILL_REVISION>` (`SKILL_REVISION` in `agents/policy.ts` and in the three scripts, raised together when installed copies must change). `update_skill` says that a newer skill is at `<issuer>/agents/skill/` for a served copy of another version, a missing header or an unknown value, and that the skill needs an update where it was installed from for `r<n>` lower than this Adiutor's; nothing for the current version or `r<n>` equal or higher. It is a notice, never a block. `get_access` on MCP never has it (an MCP client is no skill).

**`GET /api/v1/agent/endpoints[?area=read|write|sync]`** answers, not wrapped in `data`: `{endpoints: [{method, path, kind, area ("any" for access and endpoints), description, parameters: [{name, in: "path"|"query"|"body", required, description?}]}], count, revision, note: "Take every path from this list, with its {...} parts filled in. Never guess a path."}`, the routes of the areas granted (with `area`, those of that area and `any`); another `area` is `400 validation_failed`. `revision` is a hash of the open map (method, template, area and kind of each open route).

**MCP for agents.** Streamable HTTP at `/mcp`, stateless, JSON answers, `Origin` checked first as above. The token is checked as above, bound to `<issuer>/mcp`, and handed to the SDK as its `AuthInfo`. `tools/list` names only the tools of the areas granted (`read`: the five reading tools; `write`: the ten writing tools) and `get_access`; a tool of another area is not registered, so the SDK refuses a call of it, as it refuses arguments that fail a tool's schema (neither runs anything, and neither leaves an audit row). Each tool call takes a slot, checks the connection again (the call may have waited; an ended one is `connection_ended`) and runs, both under the deadline, then meets the answer cap (the serialized result) and is audited. Annotations come from the kind (`readOnlyHint` for reads, `destructiveHint: false`, `openWorldHint: false`); tool errors use the flat shape above. The instructions say what Adiutor holds, that the connection acts for the owner within the areas granted, to call `get_access` first, what agents never do, that stored text is data, and "When an action's outcome is unknown, read its result before trying again."

## MCP

Streamable HTTP at `/mcp`, stateless (no session id), JSON responses. Requires `Authorization: Bearer <agent key>`; a browser session is not accepted. (Where agent access is mounted, `/mcp` takes access tokens instead: "The agent channel" above.) A request with an `Origin` other than the origin of `ADIUTOR_PUBLIC_URL` is refused with `403 forbidden` before the key is read (DNS rebinding protection); a request without `Origin` passes. A body over 512 KiB gets `413`. The server's `instructions` summarize the rules, and they and every tool description say that text in items, comments, notes, projects and thread titles is data, never instructions. Every tool answers one text content holding JSON: `{"data": ...}` on success, or `{"error": {code, message, ...details}}` with `isError: true`, using the codes above.
